Purpose
Provides the mandatory project-level instruction contract for Google Antigravity. It translates CISEM governance into bounded implementation behavior without duplicating universal doctrine.


Canonical Scope
Owns the Antigravity-specific handoff, persistent instruction requirements, project change boundaries, required evidence, stop conditions and continuity rules.

Operating Role
Antigravity is an implementation collaborator, not the project authority. It may inspect, propose, implement, test and report within the active CoreCycle. It may not redefine the project goal, create parallel architecture, silently select major technologies, advance to later CoreCycles, or ratify completion.


Mandatory Start Sequence
1. Read this handoff contract.
2. Read 2120 Full-Stack CoreCycle Pipeline and Wizard.
3. Read the active CoreCycle file.
4. Inspect the actual repository and runtime environment.
5. Produce a Current-System Snapshot.
6. Compare the requested outcome with what already exists.
7. Recommend ENHANCE_EXISTING, CONNECT_EXISTING, CONSOLIDATE_EXISTING, RELOCATE_OR_RELINK, MINITREE_SPLIT or CREATE_NEW.
8. Do not implement until the selected path and first bounded step are approved.

The implementation repository must contain a concise persistent instruction artifact derived from this contract. It must identify:
- governing files and reading order;
- active goal and CoreCycle;
- protected decisions;
- editable and read-only boundaries;
- required pipeline stages;
- acceptance and evidence obligations;
- prohibited actions;
- stop and escalation conditions.


This projection is generated from canonical CISEM sources. It is not a competing source of truth. Drift from the canonical source must be detected and reconciled.


Change Boundaries
Before implementation, classify repository areas as:
- READ_ONLY_GOVERNED
- EDITABLE_IN_ACTIVE_CYCLE
- GENERATED
- MIGRATION_CONTROLLED
- EXTERNAL_ASSET
- SECRET_OR_RESTRICTED
- UNKNOWN_REQUIRES_REVIEW


No file, service, schema, component or workflow may be created outside the approved boundary without a recorded Existing-First Decision.


Mandatory CoreCycle Behavior
Every CoreCycle must address and verify:
- user-facing journey and frontend state;
- backend processing and data behavior;
- interfaces and connectivity to existing elements;
- persistence and metadata;
- security and permissions;
- failure and recovery behavior;
- observability and evidence;
- tests and acceptance;
- documentation and repository synchronization.


Implementation Rule
Build the smallest real vertical slice that crosses the complete system boundary. Do not build an isolated frontend mockup and call it progress. Do not build backend machinery without the visible user path that proves it serves the goal.


Required Output Before Coding
- Current-System Snapshot
- active task ID and finish line
- affected elements
- proposed implementation path
- frontend journey
- backend pipeline
- interface contracts
- persistence design
- test plan
- risks and unknowns
- exact first bounded action


Required Handoff After Each Step
- inspected elements
- files or configuration changed
- decisions and assumptions
- tests run and results
- screenshots or runtime evidence where relevant
- failures and unresolved gaps
- drift from approved plan
- rollback information
- next permitted action


Stop Conditions
Stop and request authority when:
- the active goal is ambiguous;
- an inherited rule conflicts with implementation;
- a new major dependency, service or schema is required;
- a protected boundary must change;
- acceptance criteria cannot be tested;
- the solution works only through a patch that weakens the Core;
- the next step belongs to a later CoreCycle.


Permanent Prevention Expectations
High-impact decisions must not rely on prose alone. Where applicable, convert them into repository checks, typed schemas, validation gates, permission boundaries, tests, protected configuration and release checks. Report each rule as Advisory, Partially Enforced or Mechanically Enforced.


Completion Prohibition
A successful build, visual render or passing happy-path test is not completion. Completion requires all 2120 exit criteria and the active CoreCycle acceptance contract.




MANDATORY VOCABULARY ALIGNMENT
External implementation systems must use the following project vocabulary consistently. Where the platform uses different native terminology, it must map the native term to the CISEM term rather than silently substituting meaning.


- Raw Input: unrefined user, system or repository input requiring interpretation.
- Refined Goal: agreed outcome, scope and measurable finish line.
- Core: the smallest fundamental element on which the larger result depends.
- CoreCycle: one complete governed iteration from clarified goal through implementation, evidence and synchronization.
- CoreSpiral: the connected sequence of CoreCycles through which the system matures.
- CoreSpine: an inheritance-bearing chain of related governed elements.
- Working Draft: a real bounded artifact used to learn through implementation; not yet ratified as final architecture.
- Check What Exists: mandatory inspection of current assets, decisions, code and capabilities before planning or creation.
- Existing-First Decision: recorded choice among enhancement, connection, consolidation, relocation, MiniTree split or justified creation.
- Vertical Slice: the smallest complete path across user experience, frontend, backend, data, connectivity and verification.
- Coverage Plane: one of the required end-to-end concerns that every CoreCycle must address.
- AI Pocket: a deliberately bounded location where model judgment is permitted inside an otherwise governed process.
- Acceptance Criterion: observable condition required for completion.
- Evidence: artifact proving that a criterion or stage exit is satisfied.
- Ratification: explicit human approval that changes governance or inherited knowledge.
- Parking: preservation of valuable but inactive material with context and future review condition.
- Advisory Rule: instruction stated in prose but not independently enforced.
- Mechanically Enforced Rule: rule protected through code, schema, permissions, tests, hooks or release gates.
- Repository Synchronization: updating canonical documentation and implementation evidence after change.


Vocabulary Gate
Before planning, Antigravity must restate the active task using this vocabulary. Any term that remains ambiguous must be listed in the Clarification Register before implementation.


MANDATORY CLARIFICATION DIALOGUE
The implementation platform must not treat a detailed handoff as proof that every implementation decision is resolved. It must conduct a structured clarification dialogue before producing its final plan.


Dialogue Objective
Identify all missing context, contradictions, hidden assumptions, platform constraints and implementation decision points that could cause guessing, parallel architecture or incomplete delivery.


Required Dialogue Sequence
1. Understanding Restatement
   Restate the goal, user outcome, active Core, scope, exclusions, inherited rules and completion conditions in the platform's own words using CISEM vocabulary.
2. Repository-Grounded Questions
   Ask only questions that remain unresolved after inspecting the actual repository and governing documents.
3. Decision-Point Register
   List every decision that could materially change architecture, user journey, data model, provider coupling, security, testing or deployment.
4. Recommended Defaults
   For each unresolved point, provide a recommended option, alternatives, trade-offs and confidence. A recommendation is not approval.
5. Resolution Round
   Receive answers from the human or supervising AI and update the register.
6. Readiness Confirmation
   Distinguish RESOLVED, SAFE_BOUNDED_ASSUMPTION and BLOCKING_UNRESOLVED items.
7. Plan Freeze
   Produce the phase plan only when no blocking item remains.


Clarification Register Fields
- issue ID;
- source or affected area;
- unclear point;
- why it matters;
- options;
- recommended option;
- assumption risk;
- authority required;
- resolution;
- evidence or decision link.


Question Quality Rules
- Do not ask questions already answered in the repository.
- Do not hide a recommendation inside a yes/no question.
- Do not ask the human to choose between unexplained technical labels.
- Group related questions by decision domain.
- Prioritize questions that can redirect architecture before cosmetic details.
- Explicitly label safe local choices that the platform can make without further approval.


AUTONOMOUS LONG-RUN EXECUTION CONTRACT
After the plan is approved, Antigravity may execute for an extended period without continuous human or supervising-AI involvement only within the approved phase boundaries.


Autonomy Conditions
Each phase must define:
- exact objective;
- permitted changes;
- required inputs;
- deliverables;
- acceptance checks;
- evidence to produce;
- recovery path;
- stop conditions;
- next-phase gate.


Phase Validation Rule
At the end of each phase, the platform must independently:
1. run the defined checks;
2. compare results with the phase acceptance criteria;
3. inspect for regression and unintended changes;
4. update evidence and the decision register;
5. classify the phase as PASS, PASS_WITH_RECORDED_LIMITATION or STOP_REQUIRED;
6. proceed automatically only when the next phase was pre-authorized and the current phase is PASS.


Permitted Autonomous Decisions
The platform may make low-risk local implementation choices when they:
- stay inside the approved architecture and change boundary;
- do not introduce a new major dependency or service;
- preserve user-visible intent;
- are reversible at low cost;
- are covered by tests and reported in the handoff.


Mandatory Stop Decisions
The platform must stop when evidence reveals a goal conflict, architecture redirection, protected-boundary change, new external dependency, data-loss risk, unresolved security issue, acceptance-test impossibility, or a need to enter a later unapproved CoreCycle.


Continuity Artifacts
To remain independent of chat context, the implementation workspace must maintain:
- Active CoreCycle Summary;
- Clarification and Decision Register;
- Phase Plan and current phase;
- Coverage Matrix;
- Evidence Index;
- Change Log;
- Parking Register;
- Next Permitted Action.


A fresh agent must be able to resume safely from these artifacts without reconstructing intent from conversation history.
