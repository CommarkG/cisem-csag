## 1. Principles & Goals

The **CISEM Exchange Protocol (CXP)** V1.2 implements the **Executable Governance Principle (EGP)**: every governance rule must exist as a human-readable specification, a machine-readable contract, and be validated by an automated enforcement script.

To eliminate concurrency risks, state contradictions, and overwriting issues, the protocol is **fully event-sourced and append-only** at the exchange layer.

---

## 2. Immutable command data vs derived state

Each exchange packet structure is divided into three distinct classes:

1. **`immutable_request`**: Created once by the Cloud Orchestrator at the start of a cycle. It contains the schema metadata, governance conditions, and requested execution intent. It can **never** be edited after publication.
2. **`event_stream`**: An append-only list of state-transition event objects. No events may be edited or deleted once recorded.
3. **`derived_view`**: A local projection generated by sequentially replaying the `event_stream`. The keys in this view (e.g. `current_state`, `response`, `audit`, `lessons_learned`) are derived parameters and are **never** authoritative. They can be dynamically rebuilt at any time.

```yaml

identity: {}
immutable_request:
  header: {}
  repository_target: {}

  packet_hash: ""

```

## 3. Layer Isolation Principle

The protocol enforces clean separation of concerns:
- **Protocol Layer**: Defines the schema structures, event models, lifecycle rules, ownership rules, and integrity checks. This layer has no project business rules.
- **Project Layer**: Supplies concrete governance values (e.g., acceptance criteria content, folder paths, branch names).
- **Platform Layer**: Adapters (e.g., Antigravity, Claude Code) implement the execution boundaries.
- **Transport Layer**: Defines the medium (e.g. Google Drive, Git, local filesystem) used to exchange packets.

---

## 4. Capability Registry Integration

Before claiming a packet, the adapter must check the intent requirements in the **Intent Registry** against its active capabilities in the **Capability Registry** (`2026-08-05__CISEM__CXP__CapabilityRegistry__V1.2.yaml`). Claims are blocked if required capabilities (e.g. `GIT_CLIENT`, `PYTHON_3`) are missing.

## 6. Event Stream Validator Rules

An automated validator within each adapter must run before claiming, executing, or auditing a packet. The validator verifies the following ten checks:

1. **Start Constraint**: The first event in `event_stream` must be `PACKET_CREATED`.
2. **Sequence Beginning**: The first event's `sequence_number` must be exactly `1`.
3. **Contiguity Check**: No gaps in `sequence_number` (e.g. `[1, 2, 3...]`).
4. **ID Uniqueness**: No duplicate `event_id` keys allowed.
5. **Chain Verification**: Each event's `previous_event_id` must reference the exact ID of the immediately preceding event.
6. **State Transition Validity**: Every event transition (`from_state` -> `to_state`) must match a transition defined in the transition matrix.
7. **Actor Scope Check**: The event's actor must have authority to emit the event.
8. **Liveness Check**: A packet that has reached a terminal derived state (`ARCHIVED`, `FAILED`, `CANCELLED`) cannot receive any further events.
9. **Tampering Verification**: Recomputes the content hash of every event in the sequence to detect modification.
10. **Replay Validation**: Replays the stream to verify that derived view projections match values written in `derived_view`.
