# CoreSpiral Methodology Specification: Context-Adaptive Planning & Implementation

1.1. **Purpose & Core Intent**:
This document formalizes the **CoreSpiral Methodology** as the mandatory system for structuring, designing, and executing any non-trivial development plan within the Cisem CsAg platform. It replaces all legacy rigid milestone-based planning models with an organic, inheritance-driven framework.

1.2. **Methodology Overview**:
The CoreSpiral methodology matures complex systems through concentric planning and implementation loops called **CoreCycles**. Each cycle is designed to map and resolve elements starting from the deepest platform core and spiraling outwards as dependencies are unlocked.

---

## 2. Axioms of CoreSpiral Execution

2.1. **AX-SPIRAL-01: Non-Rigid CoreCycles**:
- CoreCycles do not carry fixed, pre-defined functional definitions (e.g., there is no rule stating "Cycle 3 is always the UI cycle" or "Cycle 1 is always the Database cycle").
- Instead, CoreCycles are dynamically defined per task context, adhering to a strict **inheritance logic**: deep core foundations must be established first, and subsequent cycles build outwards from those foundations.

2.2. **AX-SPIRAL-02: Flexible Pillar Lifecycles (Concentric Insertion)**:
- Architectural considerations (Pillars) are not required to exist across all CoreCycles. A pillar can "begin" or "end" in any cycle based on the state of the project.
- Crucial foundational pillars are introduced early (VerticalSlice 1 & 2) to build the structural support needed for other features.
- A highly important feature or pillar may not even appear until VerticalSlice 3 or 4 because it depends on core capabilities that must be created and verified in VerticalSlice 1 & 2 first.

2.3. **AX-SPIRAL-03: Variable Maturity Exit**:
- A topic or pillar can reach maturity at any point during the spiral (e.g., in VerticalSlice 2) and will simply not appear in VerticalSlice 3 or beyond. Once verified as mature, it transitions to a read-only stable dependency.

## 3. Formalized CoreSpiral Execution Template

When a plan is flagged as "non-trivial" (having a broad blast-radius or complex multi-system dependencies), developers and AI models must structure their proposals using this addressable grid:

```
[CoreSpiral Implementation Plan]
 ├── VerticalSlice 1: Deep Core Foundation (Matures Core components, creates dependencies)
 ├── VerticalSlice 2: Connectivity & Security (Wires communication, sets bounds)
 ├── VerticalSlice 3: Pipeline & Quota Integrations (Implements actions & overlays)
 └── VerticalSlice 4: Outer Verification & Gates (Hardens gates, promotions)
```

### 3.1. Template VerticalSlice Structure:
1. **Focus**: What is the target maturity level of this cycle?
2. **Inherited Dependencies**: What elements from previous cycles or existing code are required to boot this cycle?
3. **Pillars Active**: Which architectural considerations begin, mature, or terminate in this cycle?
4. **Executable Proof**: What mechanical validation test proves this cycle has reached its finish line?
