================================================================================
CISEM ARCHITECTURAL RESEARCH BRIEF: #70 CONSOLIDATION & OPTIMIZATION BY ONE SOURCE OF TRUTH USED BY MULTIPLE ELEMENTS
================================================================================

1. INTRODUCTION & INDUSTRY CONTEXT
--------------------------------------------------------------------------------
Topic Overview:
Enterprise software architectures degrade when multiple subsystems duplicate state, reinvent schemas, or establish competing authorities. "Consolidation & Optimization by ONE SOURCE OF TRUTH" dictates that every foundational data model (Identity, Customer Accounts, Catalog Items, Status Libraries, Document Artifacts, and Gate Registries) must have exactly ONE authoritative source of truth that is consumed universally across all backend APIs, frontend UI components, AI agents, and pre-commit audit gates.

Needs & Business Pains:
Platforms frequently suffer from "Data Drift" and "Split-Brain Architecture." For example:
- Defining customer account status in 3 different places (a frontend UI state enum, a backend Python dict, and an un-indexed SQL string column).
- Storing duplicate catalog item prices in both a CRM deal table and a proposal draft table without a central historical reference.
- Maintaining separate permission matrices for web apps, API gateways, and background worker queues.
This leads to inconsistent UI readouts, silent data corruption, security bypasses, and massive developer overhead trying to keep fragmented models in sync.

Challenges:
- Eliminating Shadow Registries: Identifying and deprecating "shadow tables" or inline hardcoded arrays created by different development passes.
- Balancing Decoupling with Centralization: Ensuring central registries (such as status_library or lookup_registry) provide a single source of truth without creating bottleneck performance bottlenecks.
- Enforcing Schema Authority Across Layers: Translating Postgres database constraints (SQL DDL) into TypeScript types (Zod/Pydantic schemas) and AI Agent prompt contexts seamlessly.

Common Gaps & Mistakes:
- Dual-source of truth: Client components maintaining local state arrays for status options while backend APIs maintain a separate database table.
- Updating an entity's schema in the database without propagating the changes to frontend UI forms and AI agent system prompts.
- Relying on written documentation or developer discipline instead of automated pre-commit gate checks (LGG/ATV) to enforce single-source-of-truth rules.

Common Solutions Available & What We Can Do Better:
- Standard Solution: Centralized relational database tables with REST endpoints.
- What We Can Do Better: CISEM Universal Single Source of Truth Engine: 
  1) Database Level: Single canonical tables (status_library, customer_accounts, crm_customers, catalog_items, _migration_ledger).
  2) API Level: Unified Pydantic / OpenAPI schema contracts used by both backend routes and auto-generated TypeScript frontend stores.
  3) Governance Level: Hardcoded pre-commit gate checks (cisem_gate.py Phase 11 & Phase 22) verifying zero duplicate definitions across git trees.


2. PLATFORM CONTEXT & OPTIMAL USAGE
--------------------------------------------------------------------------------
What Exists in Our Platform:
- Single Source of Truth Registries (backend/src/backend/migrations.sql):
  - status_library & state_transitions: Authoritative status codes and allowed state transitions across the entire platform.
  - lookup_registry: Centralized key-value lookup for platform-wide dropdowns and options.
  - crm_customers vs customer_accounts: Clear entity boundary segregation between platform SaaS tenants (customer_accounts) and CRM client buyers (crm_customers).
  - _migration_ledger: Authoritative database migration history ledger.
- Governance Single Source of Truth (cisem_core/):
  - GEMINI.md & AGENTS.md: Canonical system instructions and naming laws.
  - cisem_gate.py: Single source of truth for pre-commit verification rules.

Best Way to Use It:
- Consume status_library for ALL status dropdowns in frontend UI components instead of hardcoding static string arrays.
- Consume state_transitions trigger (enforce_state_transition()) to validate state changes centrally at the database boundary.
- Export OpenAPI JSON schemas from FastAPI backend routes directly to auto-generate TypeScript interfaces for frontend Zustand stores, guaranteeing zero schema drift.


3. BACKEND SENSITIVE POINTS NEEDING ATTENTION
--------------------------------------------------------------------------------
- Database-First Schema Single Source of Truth: The SQL DDL in migrations.sql (or normalized migration scripts) must remain the ultimate authority. Python models and Pydantic schemas must derive directly from SQL definitions, never vice versa.
- Atomic Shared Lookups: When looking up status codes or custom library values, use indexed foreign key joins or cached lookup functions to prevent N+1 query overhead.
- Centralized RLS Policy Logic: RLS tenant isolation policies (USING (tenant_id = current_tenant_id())) must be declared on base tables centrally, ensuring all API routes automatically inherit tenant containment.


4. FRONTEND SENSITIVE POINTS NEEDING ATTENTION
--------------------------------------------------------------------------------
- Zero Hardcoded Option Arrays: Frontend views (ListView, AdminView, Form Modals) must fetch status options, tag libraries, and role definitions from backend API endpoints (/api/v1/lookups) or global Zustand stores initialized at session start.
- Single Source UI Stores: Shared UI state (theme mode, active tenant context, user roles, navigation history) must reside in a single centralized store (useUIStore.ts), preventing conflicting component state.
- Uniform Component Rendering: Sibling UI elements must read display properties (labels, icons, color tokens) from the single-source design system tokens, enforcing visual consistency.


5. WHAT MUST BE WIRED
--------------------------------------------------------------------------------
- Wire status_library and tag_library endpoints (/api/v1/lookups) directly to frontend dynamic dropdowns and multi-select filters.
- Wire customer_accounts and crm_customers tenant boundaries to all client-facing and internal management APIs.
- Wire database state transition rules (enforce_state_transition()) to frontend action buttons, visually disabling invalid state transition controls.


6. WHAT MUST BE HARDWIRED
--------------------------------------------------------------------------------
- Hardwire pre-commit gate Phase 11 (cisem_gate.py) to scan codebase changes for duplicated axiom, principle, or status definitions.
- Hardwire Postgres foreign key constraints referencing central libraries (status_library, lookup_registry).
- Hardwire single-source-of-truth file resolution in API endpoints (/api/download) searching process.cwd(), public/, and brain directories deterministically.
